What is prompt caching — and when should you use it?

Caching discounts what you re-read. It charges more for the first write.

Static content — a system prompt, a playbook, a tool set — can be marked cacheable. Call 1 pays a write premium (1.25× input). Every repeat call reads the cached block at 0.1× input — 90% off. Caching only nets out once the static block is re-read enough times to cover the write cost. A one-shot prompt pays more, not less. TTL default is 5 minutes, resetting on each read; a 1-hour option exists at 2× write cost. Minimum block size: 1,024 tokens (2,048 on Haiku — small blocks there silently fail to cache).

Lever 01

Route to the right tier

Defaulting every task to Opus is the costliest habit in the room. Most "medium" work belongs on Sonnet; routing/extraction belongs on Haiku. Opus is for reasoning that actually justifies the premium.

Try it: send the format job to Opus, then to Haiku.
Lever 02

Cache what never changes

A playbook, a system prompt, a long spec — re-sent on every call — is pure waste. Cache it once and read it back at a tenth of the price. The bigger the static block and the more calls, the more dramatic the drop.

Caveat: the first write costs extra. One-shot prompts don't benefit.

Under the hood · how caching actually fires

Speed

It's latency, not just cost

A cache hit skips re-reading the prefix entirely, so follow-ups feel instant instead of lagging while a 50-page doc is re-processed. The UX win often sells the room faster than the bill does.

Warmth

The clock resets on every use

Each read pushes the 5-minute timer back, so an active support bot or sales rep keeps the cache alive all day. Go idle past the window and it evaporates — a 9am-then-3pm pattern caches nothing.

Entry gate

A bulk discount, not a coupon

Caching won't trigger below 1,024 tokens (2,048 on Haiku). It's built for substantial playbooks, system instructions and tool sets — not one-line prompts. Small reference, no discount.

Leverage

A high-frequency amplifier

The more often the same static context is reused, the harder caching pays off. It turns high-volume workflows from cost centres into optimised systems — and does nothing for low-frequency tasks.

Prefix architecture · the #1 rule

Stable content first — the cache is exact-match

One changed character — a stray space, a timestamp, a reordered tool — invalidates the whole prefix. Claude processes in a fixed order, so put everything static before anything variable:

Tools→ System◆ breakpoint→ Messages (variable)
The longhand trap · most common miss

Strings can't carry cache_control

The shorthand string format has nowhere to attach a breakpoint. Move system prompts and blocks to the object form:

// ✗ shorthand — silently never caches
system: "You are a code reviewer…"

// ✓ longhand object — breakpoint attaches
system: [{ type:"text", text:"You are…",
  cache_control:{ type:"ephemeral" } }]
Breakpoints

Four, placed deliberately

Up to 4 manual cache_control:{type:"ephemeral"} breakpoints per request — typically at the end of the tools array and the system prompt. If you mix TTLs, 1-hour blocks must precede 5-minute ones.

Concurrency

Clone before you inject

In multi-agent loops or shared microservices, mutating the tools array or system object in place can persist cache headers across calls. Defensively clone them before attaching ephemeral control.

Verify

Trust the usage fields, not the vibe

Confirm hits in the response: cache_read_input_tokens should be > 0 on repeat calls, with cache_creation_input_tokens on the first. Zero reads on call two means your prefix broke.
